# Remote Static Drug API via GitHub Pages

Goal: keep the desktop/mobile client lightweight. The local app keeps the core seed database, and only when a local lookup misses can the user enable a GitHub Pages hosted static JSON API as a remote fallback.

## Build Flow

1. GitHub Actions runs `Build Static Drug API` on push, schedule, or manual dispatch.
2. The workflow runs `build-public-api`, which starts from DDInter/local override facts, then enriches selected substance terms through every directly usable open API adapter: RxNav, ChEMBL, DailyMed, openFDA label, and PsychonautWiki.
3. Optional normalized fact files under `data/optional` and `data/overrides` are merged in the same pass, so local exports from FooDrugs, OnSIDES, PharmGKB/ClinPGx, or other open datasets can be added without changing the mobile client.
4. `build-public-api` writes both mobile seed files and the GitHub Pages static JSON API under `public/api`.
5. After the base seed + static API are built, `tools/export_dose_overlay.py` streams all six source-layer caches (openFDA, DailyMed, ChEMBL, FooDrugs, OnSIDES, PharmGKB) and writes overlay endpoints under `public/api/`.
6. `actions/deploy-pages` publishes `public/` to GitHub Pages.

## Static API Paths

GitHub Pages does not run a dynamic backend. The API is therefore a static file API:

### Core Seed Endpoints

| Endpoint | Description |
|---|---|
| `api/manifest.json` | API version, dataset version, counts, path templates, overlay keys, and online library package metadata. |
| `api/search/index.json` | Compact search index. The client downloads it and filters locally. |
| `api/search/shards/{key}.json` | Prefix-sharded search lookups for lazy loading. |
| `api/substances/by-id/{hash}.json` | One substance detail record. |
| `api/interactions/by-substance/{hash}.json` | DDI/DFI rows involving one substance. |
| `api/dose-rules/by-substance/{hash}.json` | Dose threshold rules involving one substance. |
| `api/sources/index.json` | Source-layer summary showing which upstreams contributed facts. |
| `api/packages/full/manifest.json` | Full fused online package metadata and checksum. |
| `api/packages/full/fused-online-library.zip` | Optional full online library package for review/import tools; local clients do not download it automatically. |

### Dose Overlay Endpoints

| Endpoint | Description |
|---|---|
| `api/dose-candidates/by-substance/{hash}.json` | Label-derived dose mention snippets per substance. |
| `api/dose-candidates/manifest.json` | Record count, substance count, `max_per_substance`, and policy text. |
| `api/overdose-warnings/by-substance/{hash}.json` | Overdose warning excerpts per substance. |
| `api/overdose-warnings/manifest.json` | Record count, substance count, and policy text. |

### Content Overlay Endpoints

All content overlays are generated by `tools/export_dose_overlay.py` via `--max-content-per-substance` (default 24). Each overlay writes a per-substance JSON file plus a `manifest.json` under its own directory.

| Endpoint | Fact Types | Policy |
|---|---|---|
| `api/drug-effects/by-substance/{hash}.json` | `drug_effect` | Label indications, purpose, pharmacodynamics, and ChEMBL mechanism evidence snippets. |
| `api/drug-effects/manifest.json` | — | Record/subject counts, `max_per_substance`. |
| `api/pharmacokinetics/by-substance/{hash}.json` | `pharmacokinetics` | Structured PK values and label excerpts; not individualized dosing advice. |
| `api/pharmacokinetics/manifest.json` | — | Record/subject counts, `max_per_substance`. |
| `api/enzyme-relations/by-substance/{hash}.json` | `enzyme_relation` | Extracted CYP and transporter relations for downstream interaction review. |
| `api/enzyme-relations/manifest.json` | — | Record/subject counts, `max_per_substance`. |
| `api/label-sections/by-substance/{hash}.json` | `label_section` | Bounded DailyMed/openFDA label excerpts for traceability; evidence text, not clinical instructions. |
| `api/label-sections/manifest.json` | — | Record/subject counts, `max_per_substance`. |
| `api/safety-warnings/by-substance/{hash}.json` | `safety_warning` | Label warning excerpts and risk wording; machine extraction must not override higher-trust curated rules. |
| `api/safety-warnings/manifest.json` | — | Record/subject counts, `max_per_substance`. |
| `api/interaction-signals/by-substance/{hash}.json` | `interaction_signal` | Label interaction excerpts; review-required evidence, does not replace DDInter risk rules. |
| `api/interaction-signals/manifest.json` | — | Record/subject counts, `max_per_substance`. |
| `api/food-interactions/by-substance/{hash}.json` | `food_interaction` | FooDrugs text-mined food/bioactive-drug candidate signals. |
| `api/food-interactions/manifest.json` | — | Record/subject counts, `max_per_substance`. |
| `api/adverse-signals/by-substance/{hash}.json` | `adverse_event` | OnSIDES label-derived adverse event signals; not incidence rates or causal attribution. |
| `api/adverse-signals/manifest.json` | — | Record/subject counts, `max_per_substance`. |
| `api/pgx/by-substance/{hash}.json` | `pgx_relationship`, `pgx_clinical_annotation`, `pgx_drug_label`, `pgx_guideline` | PharmGKB/ClinPGx gene-drug, label, and guideline evidence for review; not individualized prescribing recommendations. |
| `api/pgx/manifest.json` | — | Record/subject counts, `max_per_substance`. |

Configure the local app with the `/api` base URL, for example:

```text
https://<your-name>.github.io/<repo>/api
```

### Per-overlay manifest fields

Each overlay `manifest.json` contains:

| Field | Description |
|---|---|
| `generated_from` | Source layer file paths that produced this overlay. |
| `records` | Unique deduplicated record count (by `fact_id` or content hash). |
| `subjects` | Number of substances with at least one record. |
| `max_per_substance` | Cap applied during export; `null` means no cap. |
| `policy` | Machine-readable safety/usage policy string for this overlay type. |

## Manual Dispatch and `max_content_per_substance`

`tools/export_dose_overlay.py` accepts `--max-content-per-substance` to cap the number of exported content rows per substance per overlay. The default is 24; set to 0 to export all rows.

CI uses `--max-content-per-substance 24` for GitHub Pages to keep file sizes manageable. When the full dataset exceeds 25 MiB per file or 20,000 total files (Cloudflare Pages limits), either lower this cap or increase shard granularity.

Typical manual dispatch for local testing:

```text
python tools/export_dose_overlay.py \
  --api-dir public/api \
  --max-content-per-substance 24 \
  --fact-json .cache/metabolic-source-facts/openfda_label/evidence_facts.json \
  --fact-json .cache/metabolic-source-facts/dailymed/evidence_facts.json \
  --fact-json .cache/metabolic-source-facts/chembl/evidence_facts.json \
  --fact-json .cache/metabolic-source-facts/foodrugs/evidence_facts.json \
  --fact-json .cache/metabolic-source-facts/onsides/evidence_facts.json \
  --fact-json .cache/metabolic-source-facts/pharmgkb/evidence_facts.json
```

## PWA Consumption

The PWA fetches overlays through `ApiClient.fetchBundle()` in `src/lib/api.ts`:

1. Fetch `search/shards/{key}.json` to get `SubstanceSummary` items.
2. Each `SubstanceSummary.paths` contains resolved paths for all registered overlays (`drug_effects`, `pharmacokinetics`, `enzyme_relations`, `label_sections`, `safety_warnings`, `interaction_signals`, `food_interactions`, `adverse_signals`, `pgx`).
3. `fetchBundle()` issues parallel `safeFetch()` calls for each overlay path. Missing or empty overlays return `[]` gracefully.
4. The substance detail file (`substances/by-id/{hash}.json`) also stores per-overlay record counts (`drug_effect_count`, `pharmacokinetic_count`, `enzyme_relation_count`, `label_section_count`, `safety_warning_count`, `interaction_signal_count`, `food_interaction_count`, `adverse_signal_count`, `pgx_count`).

**Note on food_interactions**: FooDrugs facts carry dual `subject_ids` (drug + food/bioactive subject). The file is indexed under the **drug** substance ID. Manifest record counts are deduplicated by unique `fact_id`, so the same fact is not double-counted even though it appears in both the drug and food substance paths.

**Note on pgx**: The four PharmGKB fact types (`pgx_relationship`, `pgx_clinical_annotation`, `pgx_drug_label`, `pgx_guideline`) are merged into a single `pgx/by-substance` endpoint per substance. Each row retains its `fact_type` field for UI disambiguation.

## Safety Policy

All overlays follow the project's evidence tier model. The key rules that apply to overlay consumers:

### Universal Rules

```text
Unknown does NOT mean safe.
Low confidence must NOT override or downgrade High / Medium confidence.
Signal / Community tiers must NOT downgrade Regulatory / Guideline / CuratedDB risks.
Machine-extracted candidates are NOT clinical recommendations.
```

### Per-Overlay Policies

| Overlay | Source Tier | Policy |
|---|---|---|
| drug_effects | Regulatory / CuratedDB | Label indications, purpose, pharmacodynamics, and ChEMBL mechanism evidence snippets. |
| pharmacokinetics | Regulatory / CuratedDB | Structured PK values and label excerpts; not individualized dosing advice. |
| enzyme_relations | Regulatory / CuratedDB | CYP and transporter relation evidence for downstream interaction review. |
| label_sections | Regulatory | Bounded DailyMed/openFDA label excerpts for traceability; evidence text, not clinical instructions. |
| safety_warnings | Regulatory | Label warning excerpts; machine extraction must not override higher-trust curated rules. |
| interaction_signals | Regulatory | Label interaction excerpts; review-required evidence, does not replace DDInter risk rules. |
| food_interactions | Signal | FooDrugs text-mined food/bioactive-drug candidate signals. Low-confidence, non-causal, must not downgrade regulatory or curated evidence. |
| adverse_signals | Signal | OnSIDES label-derived adverse event signals; not incidence rates or causal attribution; use only as low-confidence review cues. |
| pgx | Guideline | PharmGKB/ClinPGx gene-drug, label, and guideline evidence for review; not individualized prescribing recommendations. |

### FooDrugs Specifics

- FooDrugs `food_interaction` facts expose the drug as `subject_ids[0]` and the food/bioactive as `subject_ids[1]`.
- Each row includes `signal_policy: "low_confidence_text_mined_non_causal"`.
- Manifest `records` count uses unique `fact_id` deduplication.

### OnSIDES Specifics

- Each row includes `signal_policy: "label_derived_signal_not_incidence_or_causality"`.
- The `score` field reflects OnSIDES model confidence, not clinical severity.
- The PWA also supports a live openFDA FAERS fallback (opt-in, sends substance names to openFDA); this is separate from the static OnSIDES overlay.

### PGx Specifics

- Each row includes `policy: "evidence_only_no_individualized_prescribing"`.
- `gene`, `genes`, `variants`, `phenotypes`, `level_of_evidence`, `testing_level`, `has_prescribing_info`, `has_dosing_info` fields are populated when available from PharmGKB.
- PGx does NOT generate individualized prescription advice. It surfaces evidence for professional review.

## Local Boundary

The desktop/mobile app remains local-first. It keeps the original local seed, private journal, and profile storage. The online library is a remote fallback and review source: it can answer misses through static JSON paths, while the full package is only for explicit tooling or future import flows.

## Privacy Boundary

Remote fallback is off by default. When enabled, the browser requests remote static files only after a local miss or when a cached remote substance is used. The remote host can see file requests for the search index and substance IDs. Keep the option disabled if no query should leave the device.

Do not send personal profile, journal entries, dose history, or locally inferred risks to the static remote API. The adverse signal live fallback (openFDA FAERS) is opt-in and sends substance names/aliases to a third-party service; keep it user-visible and consent-based.

## Large Label Sources

openFDA and DailyMed bulk label archives are too large to keep on the client. The hosted build therefore uses their public search APIs for high-value candidate terms by default. Full bulk archives should be processed by a workstation into normalized EvidenceFact JSON, then placed under `data/optional` for fusion and publication.
